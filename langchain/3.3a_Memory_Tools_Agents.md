Up to this point we learned:

* LLMs → generate text

* Chat Models → hold conversations

* Prompts / Prompt Templates → give instructions

* Output Parsers → structure responses

* Chains / Runnables / LCEL → connect components

The next three concepts are what turn a chatbot into something that can remember, use external systems, and make decisions.

### 3.3 Core Concepts — Memory, Tools & Agents

### The Big Picture

Think of building a human assistant.

Memory

What has happened before?

Tools

What actions can I take?

Agents

Which action should I take next?

A useful mental model:

* Memory = context

* Tools = capabilities

* Agents = decision making

### 1. Memory

### Definition

Memory stores information from previous interactions so the model can use it later.

Without memory, every request is independent.

### Why memory exists

A plain LLM is stateless.

### Without memory

* User: “My name is Raj.”

* User: “What is my name?”

* Model: “I don’t know.”

### With memory

* User: “My name is Raj.”

* User: “What is my name?”

* Model: “Your name is Raj.”

That is the entire purpose of memory.

### Real-world analogy

Imagine talking to a doctor.

* If the doctor forgets everything after each sentence, the conversation is useless.

* If the doctor remembers your history, symptoms, and medications, the interaction becomes personalized.

Memory gives an AI assistant the same continuity.

### Types of memory

| Type                | Keeps                |
| ------------------- | -------------------- |
| Conversation Buffer | Entire chat          |
| Window Memory       | Last N messages      |
| Summary Memory      | Compressed history   |
| Persistent Memory   | Data across sessions |

### Conversation Buffer

### What it does

Stores the full conversation history.

### When to use

* Short conversations

* Customer support

* Coding help

* Tutoring sessions

### Limitation

History grows forever → more tokens → higher cost.

### Window memory

### What it does

Keeps only the most recent N messages.

Example: last 5 exchanges.

### Why it exists

Most conversations only need recent context.

### Best practice

* Chatbots: 5–10 turns

* Coding assistant: 10–20 turns

* Long tutoring: use summarization

### Summary memory

### What it does

Instead of storing everything, the model periodically creates a summary.

Example:

* Raw: 200 messages

* Summary: “User is learning LangChain and completed LCEL.”

### Why it’s powerful

You keep important facts while dramatically reducing token usage.

### Persistent memory

### What it does

Stores information in a database.

Examples:

* User preferences

* Learning progress

* Past quiz scores

* Favorite programming language

This is exactly what you’re building in your AdaptiveAI Tutor project.

### Modern LangChain approach

In current LangChain, memory is usually handled through message history and LangGraph state, rather than the older `ConversationBufferMemory` abstractions.

### Runnable example (recommended)

Install:

Bash

```
pip install -U langchain langchain-openai
```

Code:

Python

Run

```
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage

# Simulated conversation history
history = [
    HumanMessage(content="My name is Raj."),
    AIMessage(content="Nice to meet you, Raj!")
]

# New user message
history.append(HumanMessage(content="What is my name?"))

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)

response = model.invoke(history)

print(response.content)
```

Expected output:

Your name is Raj.

### When NOT to use memory

Avoid memory for:

* One-shot summarization

* Translation

* OCR

* Independent API requests

* Batch processing

Memory adds cost and complexity.

### Common mistakes

Common mistakes

* Sending the entire chat forever.

* Storing sensitive data without protection.

* Assuming the model remembers previous API calls automatically.

### Best practices

Best practices

* Use window memory for most chatbots.

* Use summary memory for long conversations.

* Persist only information that is genuinely useful later.

* Store memory outside the LLM (database, Redis, SQLite, etc.).

### 2. Tools

### Definition

A Tool is a function the LLM can call to interact with the outside world.

Examples:

* Search the web

* Query a database

* Run Python code

* Send an email

* Read a PDF

* Check the weather

* Calculate a number

### Why tools exist

An LLM can generate “2 + 2 = 4”, but it cannot reliably:

* access live stock prices,

* query your company database,

* execute code,

* call external APIs.

Tools provide those capabilities.

### Analogy

Think of a chef.

* The chef has knowledge (LLM).

* The kitchen has equipment (Tools).

* Knowing a recipe is not enough—you need an oven, knife, and stove.

### Creating a tool

### Runnable example

Python

Run

```
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b

# Direct tool invocation
result = multiply.invoke({"a": 6, "b": 7})

print(result)
```

Expected output:

### 42

### What the docstring does

This is critical.

The LLM reads:

* the tool name (`multiply`)

* the description/docstring

* the argument schema

Poor descriptions lead to poor tool selection.

### Good vs bad descriptions

Good

`Multiply two integers and return the product.`

Bad

`Does math.`

### When to use tools

Use tools when the answer depends on:

* Current information (weather, news, prices)

* Private data (company DB, CRM, documents)

* Exact computation (finance, engineering, statistics)

* Side effects (send email, create ticket, book meeting)

### Advantages

* Access to live data

* Deterministic computation

* Integration with existing systems

* Reduced hallucinations

### Limitations

* External APIs can fail.

* Tools add latency.

* Authentication must be managed securely.

* The model may choose the wrong tool.

### Best practices

Tool design checklist

* Keep tools small and single-purpose.

* Use clear names and docstrings.

* Validate inputs with type hints.

* Return structured data (dicts) when possible.

* Handle exceptions gracefully.

### 3. Agents

### Definition

An Agent is an LLM that can decide which tools to use, in what order, and when to stop.

This is the key jump from workflow to reasoning + action.

### Chain vs Agent

| Chain                   | Agent                                    |
| ----------------------- | ---------------------------------------- |
| Fixed sequence          | Dynamic decisions                        |
| Prompt → Model → Output | Prompt → Think → Tool → Observe → Repeat |
| Predictable             | Flexible                                 |
| Easier to test          | More powerful                            |

### The ReAct loop

Most modern agents follow ReAct (Reason + Act).

* Question: “What is 17 × 23?”

* Thought: “I should calculate this.”

* Action: Call `multiply`.

* Observation: `391`.

* Final Answer: “17 × 23 = 391.”

### Modern LangChain agent API

### Runnable example

Install:

Bash

```
pip install -U langchain langchain-openai
```

Code:

Python

Run

```
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain.agents import create_agent

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)

agent = create_agent(
    model=model,
    tools=[multiply],
    system_prompt="You are a helpful math assistant."
)

response = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "What is 17 times 23?"
            }
        ]
    }
)

print(response["messages"][-1].content)
```

Expected output:

### 17 × 23 = 391

### What happens internally

The agent is effectively doing:

1

Read the user question

2

Decide a tool is needed

3

Call `multiply(17, 23)`

4

Receive `391`

5

Generate the final natural-language answer

### When to use an agent

Use an agent when:

* The required tool is not known in advance.

* Multiple tools may be needed.

* The workflow depends on the user’s request.

* You want a general-purpose assistant.

Examples:

* “Find the latest NVIDIA stock price and summarize the news.”

* “Search my documents and draft an email.”

* “Look up a customer, calculate the refund, and create a support ticket.”

### When NOT to use an agent

Avoid agents when the workflow is fixed.

Example:

```
Upload PDF
→ Split text
→ Create embeddings
→ Store in vector DB
→ Answer questions
```

That is a deterministic pipeline (RAG), not an agent problem.

### Common mistakes

Agent pitfalls

* Giving the agent too many overlapping tools.

* Using agents for simple fixed workflows.

* Not setting a clear system prompt.

* Allowing unrestricted tool access.

For your AdaptiveAI Tutor:

* Memory → student profile, quiz history, weak topics.

* Tools → quiz generator, progress analytics, study-plan creator, database access.

* Agent → decides whether to answer directly, generate a quiz, retrieve progress, or update the study plan.

That is essentially a production-grade tutoring assistant.

### Quick Comparison

StateActionDecision

| Concept | Main job                    |
| ------- | --------------------------- |
| Memory  | Remember past interactions  |
| Tools   | Perform external actions    |
| Agents  | Choose which action to take |

### Interview-ready takeaways

What interviewers want to hear

* Memory provides conversational continuity; modern LangChain typically uses message history and LangGraph state.

* Tools let an LLM interact with external systems and perform deterministic actions.

* Agents are LLMs that can reason about which tools to call and when to stop.

* Use chains for fixed workflows and agents for dynamic, decision-driven workflows.

* Good tool descriptions (docstrings + type hints) are one of the biggest factors in reliable agent behavior.

You’ve now reached the point where LangChain becomes truly application-oriented. The next major milestone is RAG (Documents → Embeddings → Vector Stores → Retrievers), which is the foundation of PDF chat, enterprise search, and knowledge assistants.
